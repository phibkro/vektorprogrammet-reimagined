# Spec 0025: An explicit Hyperdrive platform adapter (ADR 0014 stage 1; operator decision, 2026-10-29)

Status: building. Frozen when its pull request opens; later changes are dated entries under Revisions.

## Journey

Four people meet this feature. Each can do the step below on the pull request.

1. **A reviewer reads what the platform is.** `docs/system/database-platforms.md` (generated) has three tables: what the **domain asks** of a platform (per capability, the checks that a platform must show, no engine word); how the **PostgreSQL adapter answers on Hyperdrive** (per capability, the constructs it uses, each with what Hyperdrive does with it and how that is known); and the **subset that only a direct PostgreSQL connection has** (advisory locks, `LISTEN`, session `SET`, SQL `PREPARE`, …), each with the reason Hyperdrive does not take it.
2. **A developer tries to leave the subset.** She writes `select pg_advisory_lock(42)` (or a session `SET`, or `LISTEN`) in a repository of `packages/db` or in a server file of `apps/web`. `bun run test:all` fails in `packages/db` and names the construct, the file and line, and the catalogue row. A recipe that names such a construct for a capability does not type-check.
3. **A reviewer asks a deployed Preview.** `GET $PREVIEW/api/platform` answers 200 with every check that the domain requires, each `held`, measured **through Hyperdrive** with the adapter's own constructs (two transactions on two pooled connections, a savepoint, a transaction-local setting, `SKIP LOCKED`, the statements the client sends). The pull request's Preview job calls it and fails unless it answers 200. `curl localhost:3000/api/platform` under `vp dev` answers the same from a direct connection.
4. **A developer reads why `prepare: false`.** `packages/db/README.md` says what Cloudflare documents (named prepared statements: supported for `postgres.js` and `node-postgres`, other drivers "may not be supported"), what `@effect/sql-pg` does (a native wire client; `prepare: false` sends unnamed statements in one write), and what is measured and what is not. The old sentence, "Hyperdrive pools in transaction mode, so `prepare: false`", is gone: it was the wrong reason.

## Goal, constraints, values

- **Goal.** Hyperdrive is a platform of the adapter, declared once and checked, and the domain never learns the word. The domain says which properties a platform must show; `packages/db` says which PostgreSQL constructs it uses to give them and what Hyperdrive does with each; a deployed route shows the properties hold where the system runs.
- **Constraints (operator decisions, 2026-10-28/29).** PostgreSQL-specific code stays in the adapter (ADR 0014). The domain asks for capabilities (ACID, transaction boundaries), not for PostgreSQL. The transaction constructs are independent of advisory locks (no advisory lock, `LISTEN`/`NOTIFY` or session `SET`, AGENTS.md). The Hyperdrive/PostgreSQL differences are one subset that is distinct from the direct capabilities, and the types keep them apart. Effect is the adapter's language here, not the only place the platform is decided: the declaration is plain data that the page, the checks and the probe all read.
- **Values.** One declaration, many readers (generate, then test, never copy). A check cannot pass by being absent. A claim about Hyperdrive carries how it is known (`docs`, `spec 0000`, `probe`, `unverified`), and a claim that rests on the unmerged `pg-txmode` catalogue says so in the same cell.
- **Not a dependency.** `pg-txmode` (`/srv/share/projects/pg-txmode`, PRs 1, 3 and 4 of `phibkro/pg-txmode`) is under review and unpublished. This repository imports none of it. Rows of its catalogue are cross-referenced by id and commit and labelled `unmerged`; no cell that the Preview check or a test relies on rests on them alone.

## Decisions

- **D1. The domain asks, the adapter answers.** `packages/domain/src/shared/platformRequirements.ts` declares `PlatformRequirements`: for each `Capability` of ADR 0014 either the checks a platform must show (an id, the guarantee it protects, a property in the domain's words) or why the capability needs none (what is not probed, with its reason and evidence). `PlatformProbe` (`shared/platformProbe.ts`) is a port that reports checks; `platformProblems` is the one statement of what a report must hold. No SQL word, no table, no pooler.
- **D2. One declaration of the platform, in the adapter.** `packages/db/src/platform/` holds `profiles.ts` (the `hyperdrive` and `direct` connection profiles: pooling, pool size, `prepare`, `multiplex`, what each allows), `constructs.ts` (the closed set of constructs, the two subsets, and for each construct what Direct and Hyperdrive do with it, how that is known, its sources and its `pg-txmode` cross-reference), `recipes.ts` (capability → constructs) and `statements.ts` (which constructs a SQL text uses). `databaseLive.ts` reads its client settings from the profile; the literals `prepare: false`, `multiplex: false` and `MAX_CONNECTIONS_PER_REQUEST` are gone from their old homes.
- **D3. The subsets are types.** `Construct` is `PooledSafeConstruct | DirectOnlyConstruct`, two closed literal sets. `Recipe` accepts only `PooledSafeConstruct`, so a recipe that names an advisory lock does not type-check, and `Hyperdrive.allows` is `PooledSafeConstruct` by type. `DirectOnly` is exported and rendered as the third table.
- **D4. The probe uses the adapter's constructs, on the platform it runs on.** It locks the one admin-list row (the row `AggregateLocks` locks) from two transactions on two connections, asking with `NOWAIT` and with `SKIP LOCKED` while it is held and after it ended, and writes rows of the fake mailbox that it rolls back (`rollback-leaves-nothing`, `nested-scope-undoes-alone`). It never interrupts a statement (cancel behaviour through Hyperdrive is unverified, and a probe must not be the first to find out). It runs on a Preview and locally, never on production (404, as `/api/isolation`), and not as a read.
- **D5. `/api/isolation` stays.** Spec 0018 R10 and its CI step are unchanged; `/api/platform` adds the checks that need two connections or the client's own statements. Merging the two is a later decision (Not done).
- **D6. The scan is a guard.** The check that no forbidden construct appears in the SQL of `packages/db/src` and `apps/web/src` reads the string and template literals of those files with `oxc-parser` and classifies their text (`statements.ts`). It is a conservative token match on SQL text stripped of comments and quoted strings, not a SQL parser, and it does not see SQL that a program builds from parts at run time. The replacement is `pg-txmode`'s lint, which reads the PostgreSQL parser's own AST; the trigger to switch is that package being published and merged (Not done).
- **D7. `prepare: false` stays, with its true reason.** Cloudflare documents named prepared statements for `postgres.js` and `node-postgres` only (other drivers "may have worse performance or may not be supported"); `@effect/sql-pg` is a native wire client, so it is "another driver". `prepare: false` sends `Parse/Bind/Describe/Execute/Sync` in one write with no statement name, so nothing depends on how a pooler keeps names. That the unnamed path works through Hyperdrive is measured (spec 0000 results, check lines PASS); that **named** statements from `@effect/sql-pg` would work is not measured. The platform probe adds `statements-follow-the-profile` so a change of this setting fails on the platform.

## The platform, as declared

| Profile | Pooling | Client | Statements | Pool | Allows |
| --- | --- | --- | --- | --- | --- |
| `hyperdrive` | transaction (Hyperdrive) | `@effect/sql-pg`, `multiplex: false` | unnamed (`prepare: false`) | at most 2 per request | `PooledSafe` constructs |
| `direct` | none | `@effect/sql-pg` | named (`prepare` on) | 2 (the importer) | `PooledSafe` and `DirectOnly` |

`DatabaseLive` is the Hyperdrive adapter (what a Worker builds per request); `ImportDatabaseLive` is the direct one. Better Auth's own `pg` pool (`auth.ts`, `max: 2`) and EmDash's driver connect to Hyperdrive too; they are listed on the page as consumers and are not built from the profile (Not done).

## Requirements

- **R1.** The domain declares `PlatformRequirements`, `PlatformCheck`, `PlatformProbe` and `platformProblems` (D1). A `Capability` without an entry does not type-check. Every check names a guarantee id that `guarantees.ts` declares (a test reads both).
- **R2.** `packages/db/src/platform/` declares profiles, constructs, recipes and the statement classifier (D2, D3). `databaseLive.ts` and `ImportDatabaseLive` read their client settings from a profile; `runtime.ts` takes the pool size from it (the constant is gone).
- **R3.** Every recipe uses `PooledSafeConstruct` only; every construct a recipe uses has the Hyperdrive outcome `works` or `scoped`; no recipe, and no construct that `packages/db/src` uses, is an advisory lock, `LISTEN`/`NOTIFY`, a session `SET`, SQL `PREPARE`/`EXECUTE`/`DEALLOCATE`/`DISCARD`, a `WITH HOLD` cursor, an `ON COMMIT PRESERVE ROWS` table or `LOAD`. `Hyperdrive.allows` is a strict subset of `Direct.allows`, and `DirectOnly` is their difference.
- **R4.** `PlatformProbeLive` (adapter) reports, for every check that `PlatformRequirements` lists, `held` with a detail in the engine's words, and the checks of D7; a probe step that cannot run (a second connection that is not given, an unexpected SQLSTATE) is `held: false` with the reason, never a defect that hides the other checks.
- **R5.** `GET /api/platform` answers 200 and the report when `platformProblems` is empty, 500 with the problems otherwise, an empty 404 on production (the store is not asked), and the failure's own status otherwise. It is not a read (`runQuery`): it runs through `runOutcome`. `.github/workflows/preview.yml` asks it after `/api/isolation`, in the same step, on every pull request and fails unless it answers 200.
- **R6.** The forbidden-construct scan (D6) runs in `packages/db`'s tests over `packages/db/src` and `apps/web/src`; it fails with file, line, construct and catalogue row.
- **R7.** `docs/system/database-platforms.md` is generated by `bun run docs` from the two declarations and checked by `bun run check:docs`. `packages/db/README.md`, `AGENTS.md` and the header comment of `databaseLive.ts` state D7 and cite the generated page; the sentence in `packages/db/README.md` about code delivery (`Code delivery uses a separate transaction to mint, send and acknowledge a link`, stale since spec 0024) is corrected on the way.
- **R8.** The module graph and the store boundary say what the new imports are: `platformProbe`/`platform` modules of the domain, `tools/docgen` reading `@vektorprogrammet/db/platform` (pure data, no client), each with its reason.

## Failure cases

| Case | What happens |
| --- | --- |
| A required check is missing from the report | `platformProblems` names it; the route answers 500 |
| A check reports `held: false` (a lock that does not exclude, statements that are named, a second connection that is not available) | the route answers 500 with the check's id, guarantee and detail |
| The database cannot be reached | the probe's own statement is a defect, as in `IsolationProbe`: the route answers the failure's status |
| Production | empty 404, no statement |
| A forbidden construct appears in source | the scan fails the test with file, line, construct, row |
| A new `Capability` is added | `PlatformRequirements` does not compile until it says what the platform must show or why nothing |
| Hyperdrive changes a documented cell | not detected here; the row's `verified-on` date and `verifiedBy` say how old the claim is, and the Preview check is what notices a changed behaviour |

## Not done here

- **Merging `/api/isolation` into `/api/platform`** (D5).
- **Better Auth's `pg` pool and EmDash on the profile.** They connect to Hyperdrive with their own settings; the page lists them.
- **A committed-write probe of claims** (`CL2`, one winner of `ON CONFLICT … DO NOTHING RETURNING`): it would leave a committed row on a Preview. Its Hyperdrive evidence is spec 0000 (20 concurrent upserts, PASS).
- **A PgBouncer harness in CI** (pg-txmode's lane). The stand-in run recorded in the Revisions is a one-off on a developer machine.
- **`pg-txmode`'s lint and catalogue as dependencies** (D6; unpublished).
- **Named prepared statements from `@effect/sql-pg` through Hyperdrive**: not measured (D7).
- **Production**: the route answers 404 there and nothing asserts production's platform until it is deployed (spec 0018 R18 has the follow-up).

### R2 (2026-10-29): the build

What the build taught, in the order of the plan:

1. **The checks are five, not seven.** The domain asks for `lock-excludes-second-holder`, `lock-ends-with-its-transaction` (`AggregateLocks`, LK1), `held-record-is-not-handed-on` (`WorkQueue`, LS1), `rollback-leaves-nothing` (TX1) and `nested-scope-undoes-alone` (TX2). The adapter adds one of its own, `statements-follow-the-profile` (D7). A transaction-local setting would not tell a commit from a rollback (`SET LOCAL` is gone at both), so the transaction checks write a row of the fake mailbox under a random key and roll it back. Nine capabilities are not probed, each with its reason in the domain and its evidence in the adapter (`platform/evidence.ts`), and the evidence says where it was **not** measured through Hyperdrive (the exclusion constraint's SQLSTATE, conditional writes, snapshots, read-only reads).
2. **No `_tag`, no barrel, no class.** The repository's lint refuses a hand-written `_tag` literal, a barrel that re-exports 640 modules (`no-barrel-file`), and the autofix turns a `Schema.TaggedError` class into `extends new …` in a file with one such class. So `CapabilityRequirement` is two interfaces told apart by `isProbed`, `@vektorprogrammet/db/platform/*` is a wildcard subpath export (`constructs`, `profiles`, `recipes`, `statements`), and the probe's transaction ends on purpose by failing with the number of rows it saw (a SQL failure is never a number).
3. **The route does not go through `runQuery`.** `runQuery` is a read, and `readsNeverWrite.postgres.test.ts` runs every read path as a role that can only `SELECT`; the probe takes a row lock and writes rows that it rolls back, so it would fail there and should. The route runs its program with `runOutcome` over `liveRequestLayer` (both already exported for tests), so it is not counted as a read path, and says why in its own comment; a second exported runner (`runProbe`, first tried) was an alias that knip refused as a duplicate export, and a copy of `runQuery` was a clone for jscpd. The route is unauthenticated, like `/api/isolation`: on a Preview or the `main` stage it takes the admin list's row lock for a few milliseconds and writes nothing that is kept; production answers an empty 404. `GET /api/platform` is also a browser-test spec (`apps/web/e2e/platform.spec.ts`), and the answers that the two diagnostic routes share are one function (`apps/web/src/server/diagnosticResponse.ts`; jscpd found the first copy).
4. **One Preview step asks both routes.** `.github/workflows/preview.yml` loops over `isolation` and `platform` in the one step that already holds the URL check, instead of copying the URL extraction.
5. **The probe never interrupts a statement.** A pool of one connection makes the second transaction wait for a connection, and the check's timeout (15 seconds; 2 in the test) interrupts that wait, not a statement, and the holder's transaction rolls back with its fiber.
6. **The mutations ran, each on the real source and restored from a copy.**

   | Mutation | What failed |
   | --- | --- |
   | M1: the holder's `SELECT` takes no `FOR NO KEY UPDATE` | 3 of 4 tests of `platformProbe.postgres.test.ts`, 3 of 3 runs (the three lock checks) |
   | M2: the claimer asks `FOR UPDATE` without `SKIP LOCKED` (it waits for the holder) | the same 3 tests, 2 of 2 runs (the lock checks time out: "could not run") |
   | M3: the `hyperdrive` profile says `prepare: true` | the F6 test and the pool-of-one test, 2 of 2 runs; with the added assertion that the profile does not name statements (D7), the apps-layer test too |

   The pool-of-one control is a test of its own (the three lock checks fail with "could not run" and the other three are still reported).

7. **The `pg-txmode` cross-reference was compared, cell by cell, with ours.** Where both say the same: `advisory-session`, `advisory-xact`, `listen`, `notify`, `sql-prepare`, `set-session` (scoped), `set-local`, `with-hold-cursor`, `temp-table-preserve`, `on-conflict`, `savepoints`. Where ours is stronger because this repository measured it and the catalogue had no probe: `isolation-level` (`unknown` there; `GET /api/isolation` measures it on every Preview) and `unnamed-statements` (`unknown` there; slice 0000 ran every check unnamed). `row-locks` and `skip-locked` are `unknown` there and `platform-probe` here: **claimed by this pull request's first Preview run, not yet observed on Hyperdrive**; if the Preview job fails, those two cells change to `unverified` in a new Revision. The catalogue is unmerged (PRs 1, 3 and 4 of `phibkro/pg-txmode`, head `afc310d`), and a row id that it renames breaks only a pointer.
8. **Checks.** `vp check` 0 errors; `bun run check:docs`, `check:module-graph` (docgen may read `packages/db`; `tools/docgen uses packages/db`), `check:store-boundary` (one allowance: `databasePlatforms.ts`), `check:exceptions`; the domain, db, docgen and web suites named in the falsifiers; the results of `bun run ready` and the browser tests are in the pull request.
9. **A one-off run through a transaction pooler (a stand-in, not Hyperdrive, not in CI).** PgBouncer 1.25.2 (`nix shell nixpkgs#pgbouncer`) in transaction mode, `max_prepared_statements = 0`, between the test's client and the devenv PostgreSQL (`TEST_DATABASE_ADMIN_URL` pointed at it), ran `platformProbe.postgres.test.ts`. With a pool of 3 server connections the four tests passed in 4 of 4 runs, so the lock checks hold through a pooler that gives the two transactions two server connections. **It also found a defect in the first version of `statements-follow-the-profile`**: it counted every `effect%` statement in `pg_prepared_statements`, and on a shared server connection that includes what an earlier client left there (the test's own named client), so the unnamed client failed its check. The statement now carries a token that no other client has and the check counts that statement only; the same four tests then passed through PgBouncer and on the direct connection. With `default_pool_size = 1` the first test failed (123 s, each lock check timing out as "could not run"): a pooler with one server connection cannot show two transactions, and the probe says so. PgBouncer is not Hyperdrive (Hyperdrive resets a returned connection, replays `Parse` and buffers until `Sync`); the run shows that the probe finds this class of pooler fact, and nothing more. The throwaway PgBouncer was stopped and its files removed.
10. **`bun run ready` found two quality tests that the plan had not named, and the first was right.** `tools/quality/test/domainMechanism.test.ts` (spec 0018 F7: no file of the domain names an engine feature) failed on the first version of `platformRequirements.ts`, whose `NotProbed` entries carried the evidence in the engine's words (`PostgreSQL`, `SQLSTATE`, "exclusion constraint", the `*.postgres.test.ts` names). The test was pointing at a real misplacement: where something was measured names the engine and its tests, so it is the adapter's to say. The domain keeps only the reason, in its own words; `packages/db/src/platform/evidence.ts` says, for every capability, where it is shown and where it was not measured through Hyperdrive, and the generated page joins the two. `tools/quality/test/storeBoundary.test.ts` pins the production allowances outside `packages/db`: `tools/docgen/src/databasePlatforms.ts` joins the list (R8), with the reason beside it.

### R3 (2026-10-29): the first run through Hyperdrive

The pull request's Preview job ran `GET /api/isolation` and `GET /api/platform` on the deployed Worker, through Hyperdrive to Neon (GitHub Actions run 40958403556, deploy job, 21:33 UTC): **both answered 200** and the `platform` report held every check. What it observed, in the engine's words: the writer saw 1 row of its own and 0 remained after the rollback; after the nested scope failed the outer scope saw 1 of its 2 keys and 0 remained after it rolled back; **while the first transaction held the row the second was refused with SQLSTATE 55P03** (two transactions on two pooled connections); after the holder ended the second got 1 row; and a claimer that skips locked rows got 0 rows while the row was held and 1 after it ended. `statements-follow-the-profile` held too (the answer was 200). So the Hyperdrive cells that R2 item 7 marked "claimed, not yet observed" (`row-lock`, `row-lock-nowait`, `row-lock-skip-locked`, `unnamed-statements`) are observed, and `platform-probe` in those cells is true as of this date; no cell changes. What this run does **not** show: that `CancelRequest` or a request abort behaves in any way (the probe never interrupts a statement), that named statements from `@effect/sql-pg` work, or anything for production, where the route answers 404. The first run of the pull request's `checks` job (17 minutes, browser tests included) was still running when this was written.
