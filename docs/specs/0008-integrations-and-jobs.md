# Spec 0008: Integrations and scheduled jobs

**Status:** frozen when PR opens; later changes are dated entries under [Revisions](#revisions) · **Phase:** 2 exit · **Source:** brief §2–§3, §7 (accepted revisions, 2026-10-26); `docs/system/architecture.md`, `docs/system/teams.md`, `docs/system/administration.md`; INFORMATION_MODEL §9.3, §9.7, §10.1, §11.3–§11.4; ADR 0001, 0004, 0006, 0007, 0008; specs 0003, 0006, 0007.

## Journey

1. **A person is invited, a claim is decided, or a team changes.** The domain command commits its facts and outbox messages together; provider calls happen after commit, never inside the transaction.
2. **In local and Worker Preview**, an e-mail or Slack message lands in the capture sink, not at a real person or workspace. The same command and message schema run in production, where only the production adapter has real bindings.
3. **An administrator opens Integrations** and asks for a Google Workspace dry-run. The report shows, by group and account, desired state, actual state, additions, removals and unmanaged extras, without placing member addresses in logs.
4. **After comparing the report for every active team**, the operator explicitly enables Workspace writes. A later run converges the directory to the active-membership projection; if it would remove more than 20 members in one run it stops and reports the diff rather than mass-removing people.
5. **Every ten minutes**, the single Worker's `scheduled` handler dispatches registered jobs whose declared "due when" predicate is true. Each job runs as its named `System` principal and either finishes or saves its cursor for the next tick.

## Goal, constraints, values

- **Goal:** all provider effects are durable, sandboxed and recoverable; every scheduled write is an authorized, resumable job with one declared owner and schedule.
- **Constraints:**
  - **Keep the existing ports and outbox.** `packages/domain/src/shared/outbox.ts`, `packages/db/src/schema.ts` (`outbox`), `packages/db/src/repositories/outbox.ts`, and `apps/web/src/server/outboxDelivery.ts` already implement the transactional outbox, row claims and retry. Extend their tagged message and migration contracts; do not add a second queue. Every message is written with the triggering command in its transaction. `apps/web/src/server/senders.ts` already selects production transports only for `production` and a capture sink for `local` and `preview`; preserve the structural environment gate. Delivery is outside transactions. No provider call occurs inside a domain command.
  - **E-mail and Slack have real and capture adapters.** E-mail uses Cloudflare Email Service only in production; Slack uses the production Slack adapter only in production. The capture sink stores test payloads for e2e access in non-production and logs only message kind. Contact mail and Slack remain (RULE-249); Slack is not the audit log, which is `audit_log`. SMS is retired: no accepted in-system workflow sends it. Interview scheduling/reminders moved to Calendar, surveys to Google Forms, and contact sends e-mail/Slack only (INFORMATION_MODEL §8–§9.3, §9.5; RULE-106). The brief's Phase 2 SMS-adapter line is superseded by this accepted information model; no GatewayAPI credential, phone-number normalizer or SMS transport is built (RULE-175, 176).
  - **Google Workspace is a one-way projection.** The system is the source of truth; Workspace never writes back. `WorkspaceDirectory` is a service interface in `packages/domain` (new); its adapter is in `apps/web/src/server/workspace.ts` (new). Desired state is a pure function of active memberships, placements, team functions and their configured group addresses. It reconciles team groups, company accounts and membership; it does not create Team Drives (those belong to Notion/Drive, not the core). A person's company address is generated by the pure rule RULE-058, unique across persons and teams, and ends in `@vektorprogrammet.no` (RULE-178, 179). The imported existing address is kept, not regenerated. A deactivated Account is not projected as an active company account even if an engagement remains (RULE-202).
  - **Safe sync:** dry-run is the default and has no write credential. Writes require an explicit `WORKSPACE_MODE=write` switch and an operator-held production authorization. The first real dry-run must match the expected memberships of every active team before the switch can be enabled. Unmanaged Workspace entries are reported, not silently removed. A run refuses removals above 20; the limit is data in the job declaration and changing it requires a fresh diff. Provider failures remain retryable; reconciliation is idempotent.
  - **The job registry is data in `packages/domain`** (new), not a list in the Worker. Each declaration is `{ name, dueWhen, systemPrincipal, chunkSize, chunksPerTick }`; a complete set is consumed by `tools/docgen` (new), the scheduler, and tests. The one cron remains `*/10 * * * *` in `apps/web/worker.config.ts`; `apps/web/src/server.ts` dispatches registry entries, not hand-coded calls. `scheduled` runs each due job in declaration order. Cloudflare Cron limits apply: 30 s CPU for an interval under an hour, 15 min wall time per invocation, 128 MB memory. Jobs bound work by declared chunks and persist a cursor before continuing on the next tick.
  - **Single-flight without advisory locks.** `job_run` (`packages/db/src/schema.ts`, new) has a unique `(job, period)` key, `startedAt`, `endedAt`, `outcome`, `counts`, `cursor` and lease. `INSERT … ON CONFLICT DO NOTHING` claims a new period; an expired lease is taken with a conditional update. No advisory locks, LISTEN/NOTIFY or session `SET`. A partially completed job resumes from its persisted cursor. Every System principal has only the grants for its own job; no handler bypasses `authorize` (ADR 0008).
  - **The registry lists every job, including inherited ones:** `semesters` (spec 0003; due when the current semester or successor may be absent); `outboxSweep` (every tick, due messages); `endingSoon` (four weeks before semester end, once per semester); `retention` (nightly); `alumniConsent` (daily scan for ended last engagements without a request); `admissionAlerts` (when a period opens, once per period); `workspaceSync` (nightly and on an explicit dry-run request). `docs/system/administration.md`'s scheduled-jobs table is generated from the registry. No job schedule lives only in an external crontab.
  - **Every read is pure.** Read queries register in `apps/web/test/readsNeverWrite.postgres.test.ts`. Provider reads used to compute the Workspace diff happen outside a database transaction; persistence of the diff and job cursor is a System command.
- **Values:** one registry is the scheduler, its authorization policy, its recovery record and the generated documentation.

## Declarations (new kernel use)

- `Job.make({ name, dueWhen, systemPrincipal, chunkSize, chunksPerTick })` declares one scheduled program; one registry feeds the dispatcher and docgen. The registry is closed: every job has exactly one `System(name)` grant and runner.
- `JobRun` is the persisted claim and continuation record. `INSERT … ON CONFLICT DO NOTHING` claims `(job, period)`; a conditional lease update transfers an abandoned run; a cursor is committed after each chunk.
- Extend the existing `OutboxMessage` tagged union with only the provider operations required here (`Email`, `SlackPost`, `WorkspaceChange`). Keep transport-specific data behind the port and keep secrets out of persisted payloads.

## Falsifiers (definition of done)

1. **Environment separation.** The same e-mail and Slack command in local and Worker Preview creates capture records and makes no real provider request; production builds the real adapters only with production bindings. A negative control that selects the real adapter outside production is refused.
2. **No I/O in transaction.** A provider that blocks until the command commits observes the committed row before receiving a call; a rollback leaves neither a delivered message nor a provider call (real PostgreSQL, negative control).
3. **Idempotent delivery.** Repeated delivery and a crash after provider success but before acknowledgement converge without duplicate effect where the provider supports an idempotency key; failures back off and the row remains retryable. Existing `outboxDelivery.test.ts` and real-PostgreSQL claim tests cover the durable boundary.
4. **Dry-run does not write.** Against a deterministic directory fixture, the report lists exact desired/actual/add/remove/unmanaged counts, has no member addresses in logs, and makes zero mutation calls. A workspace directory with no configured group address produces a typed visible issue, not a guessed address.
5. **Write gate and cap.** With write mode off, every mutation endpoint is absent/refused. With it on, approved diffs apply idempotently; a diff with 21 removals refuses before any removal, while 20 is applied. A negative control removing the cap is detected.
6. **Job registry completeness.** A declaration check fails for an unregistered runner, duplicate `(name, period)`, missing `System(name)` grant or undocumented job. `tools/docgen` emits all seven jobs and their due conditions from the same registry; changing one declaration makes `check:docs` fail.
7. **Concurrent ticks.** Twenty concurrent real-PostgreSQL ticks for one job and period create one `job_run` and one set of effects; `INSERT … ON CONFLICT DO NOTHING` makes a second claim lose.
8. **Killed-run recovery.** Terminating a job after a committed chunk leaves a cursor; the next tick resumes and reaches the same rows/counts as an uninterrupted run, with no duplicate effects (real PostgreSQL).
9. **Budget and dispatch.** A job configured above its chunk budget continues on the next ten-minute tick; every invocation stays within its declared chunk count. Dispatch runs due jobs only and one job failure does not cancel other due jobs. A Worker Preview has no cron trigger; the job can be invoked explicitly against fake data.
10. **Production Workspace gate.** Open for the operator: run a read-only dry-run using the organisation's Workspace and compare the expected membership for every active team. Only after approval, enable the explicit switch and verify an actual write against one agreed test group. Local/provider fixture tests do not substitute for this operator-held gate.

## Open for the operator

- **Workspace credentials and ownership:** organisation-owned service account, domain-wide delegation if required, least-privilege scopes and a data processing agreement. Production dry-run and write approval are held by the operator; they do not block implementation.
- **E-mail sender domain:** production Cloudflare Email Service sender and DNS verification (SPF/DKIM/DMARC) need operator-owned domain changes and approval. Local/Preview remain capture-only.
- **Slack credentials:** organisation-owned production credential and DPA; no per-developer or personal webhook. SMS credentials are not provisioned because SMS is retired.
- **Production removal threshold:** the default cap is 20 removals per tick; any increase is an explicit operator decision after reviewing a fresh diff.

## Out of scope

SMS; Team Drives, Drive content, Notion and any reverse sync; the legacy six cron command schedules (they are not in the repository, and the registry replaces them); production credentials, DNS, and live Workspace writes without operator authority; bookkeeping adapters (spec 0012).

## Revisions

### R1 (2026-10-27): reconciliation with main `085376f`, written before code

The contract stands. The draft was written against the information model, not against the code of main. These are the facts of main that it did not have, and what each one decides. Every decision keeps the draft's falsifiers.

1. **The notification adapters exist; the slice closes three gaps in them.** `apps/web/src/server/senders.ts` has `MessageSender`, the capture sink, the production senders that refuse to build outside `production`, and `messageSenderLayer`, the one choice; `outboxDelivery.ts` has claims with leases, fencing tokens, back-off and `dead`; `sandbox.test.ts` is the first half of falsifier 1. The gaps: (a) the capture sink stores an e-mail (`captured_mail`) but keeps a Slack post only in a `Ref` that dies with the sweep's Layer, so a non-production Slack post is not reachable for a browser test; (b) a send has no stable key, so a crash after the provider answered and before the acknowledgement re-sends with nothing for a provider to deduplicate on (falsifier 3); (c) nothing observes that no provider is called inside a transaction (falsifier 2). Build: `captured_slack` beside `captured_mail`, the outbox row's id as the key that `MessageSender.send` receives (the capture sink deduplicates on it, as a provider with an idempotency key would; the real e-mail transport sends it as the message id; Slack's incoming webhook has no such key, so a duplicate Slack post after that one crash window is accepted and stated), and a real-PostgreSQL test of falsifier 2 with its negative control. No second queue, no new transport code path.
2. **Jobs are commands already (spec 0003, spec 0006 R1).** A job's work is a command with `info({ job, resource, method })`, granted to `System(job)` alone, run through `Commands.inProcess` by `apps/web/src/server/runtime.ts` (`runSemesterJob`, `runEndingSoon`, `runDelivery`), and `scheduled` calls them by hand. The registry replaces the hand-written calls and nothing else: a registered job's runner is still that System command, through `authorize`, so the registry adds the schedule, the budget and the `job_run` record and does not add a second authorization path. `SystemJob` (`kernel/principal.ts`) is the closed set of job names, and `audit_log_system_job` has a `CHECK` on it; a completeness test ties the registry to `SystemJob` in both directions, so a job cannot be a principal without a declaration, a runner and a documentation row, nor a declaration without a principal.
3. **Four jobs, not seven, on this branch.** `retention` and `alumniConsent` are spec 0007b's (in build in another worktree; their commands do not exist on main), `admissionAlerts` is spec 0009's. The registry is closed over `SystemJob` and a declaration needs a command with its grant, so the three register with their specs. This slice registers `semesters`, `outboxSweep`, `endingSoon` and the new `workspaceSync`. Falsifier 6 reads "every name in `SystemJob` has its declaration, runner, grant and documentation row, and the generated table lists exactly the registered jobs"; the file `administration.md` keeps its sentence on retention until 0007b registers it. Merge note for 0007b and 0009: add the name to `SystemJob`, a declaration to `jobs/registry.ts` and a runner to `apps/web/src/server/jobRunners.ts`; the completeness test and the type of the runner table fail until all three exist.
4. **One tick, many jobs: the cron list is generated, the cadence is declared.** The draft keeps one cron (`*/10 * * * *`) and a `dueWhen` per job; the assignment adds that the Worker's triggers are generated from the registry. Both hold: a declaration carries `schedule: { cron, status }` and `dueWhen`; `cronTriggers(Jobs)` is the distinct crons in declaration order (today one); `worker.config.ts` exports it as `CRON_TRIGGERS` and `alchemy.run.ts` and `vite.config.ts` read it, replacing `OUTBOX_SWEEP_CRON` (removed with its callers). `scheduled(controller)` runs the jobs whose `schedule.cron` is `controller.cron`, and every job when the cron is empty (the local trigger `/cdn-cgi/handler/scheduled` passes none, as spec 0003 R1 uses it), each in declaration order and each isolated from the others' failures.
5. **The schedule is an operator gate; the values are proposals, marked.** The accepted cadence is the ten-minute tick that spec 0003 and spec 0006 already run on, so the three inherited jobs are `approved`. `workspaceSync`'s nightly window (02:00 Europe/Oslo) is `proposed`. R1 originally let a proposed cadence run unchanged; R2 item 8 supersedes that behavior to keep the operator gate closed.
6. **A due job has a period, and a period is claimed once (`job_run`).** `dueWhen` is a closed list of pure rules (`EveryTick`, `Daily(hour)`, `PerSemester`, `BeforeSemesterEnd(weeks)`) that return the periods that are due at an instant (the tick's own bucket, the Oslo date, the semester's label). A request for a run is a `job_run` row too (period `request:<n>`, outcome `partial`, no cursor): the dispatcher resumes every `partial` or expired run of a job beside the periods that are due, so "a dry-run on request" and "continue next tick" are one mechanism, and a command that asks for a run (`createWorkspaceReport`) writes a row and calls no provider. `job_run` is `(job, period)` unique with `outcome` (`running`, `partial`, `done`, `failed`), `cursor` and `counts` as jsonb, `attempt` (the fencing token) and `lease_until`. A claim is `INSERT … ON CONFLICT DO NOTHING RETURNING`; a take-over is one conditional `UPDATE … WHERE outcome IN (partial, failed) OR (running AND lease expired) RETURNING`; every later write (`advance`, `finish`, `fail`) carries `attempt`, so a runner whose lease was taken over cannot write. No advisory lock, no `LISTEN`, no session `SET`.
7. **A chunk and its cursor commit together.** A cursor written after the chunk's own transaction would leave a window in which the effects are committed and the cursor is not, and the replay would double them. The runner is two steps, as `runCommandOutcome` already is: `prepare(cursor)` reads from providers outside any transaction, and `commit(prepared)` is the System command that writes the chunk's rows and calls `JobRuns.advance` in the same transaction. A killed run therefore has either the chunk and its cursor or neither (falsifier 8).
8. **Spec 0006b: no aggregate lock is needed, and the test says so.** The Workspace projection reads people, memberships, accounts and teams the way a display read does and decides no write on a table that the Person root owns, so it takes no `Locked<"Person">`. The new tables (`job_run`, `workspace_report`) hold person ids as plain integers (a snapshot outlives what it names, as `audit_log` does) and no foreign key to `person`, so the ownership closure test needs no new declaration, and a test asserts that neither table is owned or refers to a root. `job_run` is not a root's machine: its transitions are the outbox's pattern (conditional updates fenced by a token), not `Aggregates.apply`, which needs a `Locked<Root>` to write a root-owned column.
9. **Spec 0007's delivery stays as it is.** `IssueCode` and `SetCredential` are delivered by `AccountDelivery` in their own transaction (spec 0007 R1) and never reach `MessageSender`; `TransportMessage` stays `Email | SlackPost`. `WorkspaceChange` joins them as the third kind that is not a transport message: the sweep routes it to `WorkspaceWriter`. A change is a statement of state (`ensure member`, `ensure absent`, `ensure account`), so a repeated delivery is a no-op at the provider. `outbox_kind` is a `CHECK` over `OutboxMessage.cases`, so the new kind comes with a migration.
10. **Spec 0007c: names.** A command declares `resource` and `method`, and a new noun joins `NonEntityResources` first. This slice adds the noun `WorkspaceReport` and the commands `createWorkspaceReport` (`create`; an administrator asks for a dry-run), `syncWorkspace` (`":sync"`; the job's chunk, `System("workspaceSync")` alone) and the read `viewIntegrations` (a guarded page, so no pair). The generated `commands.md` lists them.
11. **The projection's inputs on main.** `person.company_email` exists (unique, lower case) and no rule enforces RULE-179 or generates an address (RULE-058): both are pure functions here (`workspace/companyEmail.ts`), and the imported address is kept. A team has no group address on main (the legacy `Team.email` was not carried over in spec 0006): `team` gains `group_email` (nullable, unique, lower case, ends in `@vektorprogrammet.no`), set by `createTeam` and `updateTeam`, and a team without one is the typed issue `NoGroupAddress` in the report, never a guessed address (falsifier 4). Placements do not exist yet (spec 0011): the desired state reads memberships active this semester (`isActive`, RULE-016), the Account's state (RULE-202) and the team's function; spec 0011 adds placements as a second source of the same function.
12. **The Google adapter is the credential gate, and the stand-ins are declared.** `WorkspaceDirectory` (read) and `WorkspaceWriter` (mutate) are two services, so a dry-run program does not have a mutation in its type. `apps/web/src/server/workspace.ts` builds, by deployment and mode: local and Preview get an in-memory directory (empty unless a test fills it) and a capture writer; production without credentials gets a directory that fails `WorkspaceUnavailable` (the report then records the desired state and the typed issue, so the operator can already compare the expected members of every team); `WORKSPACE_MODE` is `dry-run` unless it says `write`, and without it `WorkspaceWriter` is the one that refuses. No call to Google exists in this slice, and the follow-up that adds it replaces one branch of that function (read-only scopes first). Approving writes is then one value, `WORKSPACE_MODE=write`, held by the operator.
13. **Budget and limits.** A chunk is bounded by the job's `chunkSize`, a tick by `chunksPerTick`, and the Cloudflare limits of the draft (30 s CPU, 128 MB) bound both; the dispatcher stops at the chunk budget, leaves the run `partial` with its cursor and continues on the next tick.

### R2 (2026-10-27): department lists, first-membership messages and dry-run safety

1. **Department lists and the 0011 seam.** A report includes a desired mailing list for each active department. The current facts are active team memberships in that department, for people with Active accounts. `DepartmentEngagement` is the input pair `(departmentId, personId)`; the plan deduplicates by person id within that department, never by display name and never by a membership in another department. Spec 0011 adds active placements to the same fact stream and to the people read, without changing this projection's input or report contract. Main has no configured Google group address for a department list, so the report shows the desired list and does not invent a provider target or claim an actual diff.
2. **RULE-248 while Google is not provisioned.** On a person's first-ever team membership, the existing Person lock protects the history read and the `welcome_ledger` claim. The membership, unique Person-owned claim and two outbox messages commit together; a rollback commits none. Cancellation and a later membership cannot claim again. The welcome and setup guidance go to the registered private address and say that this system has not provisioned a Vektor account yet. This is an approved deviation from the legacy setup message's company-address recipient: after the operator authorizes a real Google projection and the company account is provisioned, change the one `setupRecipient` declaration in `teams/welcome.ts` to the verified company address. No provider call is inside the transaction. Delivery is at least once; only a provider with idempotency can guarantee one external effect.
3. **A requested dry-run stays dry.** An administrator's request is a `request:` period with a cryptographically random nonce; a duplicate key is a defect, never a false success. The report records `dry-run` even when scheduled writes are enabled. A scheduled run may queue writes only when both its recorded starting mode and the current mode are `write`, so turning the switch on during a partial dry-run cannot turn it into a write.
4. **Usable team groups.** `createTeam` and `updateTeam` accept the nullable group address, normalize it and enforce the company domain. The Team form edits it; a claim already owned by any person or team is a typed `Conflict`. Generated account addresses avoid both configured and directory group addresses.
5. **Import replacement protects durable activity.** The importer locks the new tables and refuses a target containing welcome claims, queued or captured messages, job runs or Workspace reports. It cannot reconstruct those records from the legacy data; `tools/import/test/roundTrip.test.ts` checks the claim and job controls.
6. **Existing invalid company addresses are visible, not guessed.** New person and team inputs enforce RULE-179. An older stored address outside the company domain is retained and reported as `InvalidCompanyAddress`; a group with an unresolved member is marked incomplete and has no calculated removals. A write-mode run with unresolved member addresses is refused before queueing any change. Inactive legacy addresses still reserve their stored value but do not prevent an unrelated report. The real browser suite exposed this case through an existing fake account fixture; the PostgreSQL regression and the input-schema test pin it.
7. **Preserving older membership history.** A planned membership can predate the ledger. Its cancellation records a Person-owned welcome claim in the same transaction before the last historical row disappears; a later membership therefore cannot send a second welcome. Already-erased legacy history cannot be reconstructed from current data.
8. **A proposed schedule is not an approval.** A proposed cadence creates no automatic period, resumes no previously automatic period, and contributes no Worker cron trigger. Explicit `request:` periods still run and resume on the existing approved ten-minute tick. The repository filters requests before its 20-row limit, so paused automatic periods cannot starve a requested report. Changing `status: "proposed"` to `"approved"` in the one job declaration installs its cron and permits the automatic cadence; a real-PostgreSQL regression tests both states and the backlog.
9. **Durable account assignment and one address namespace.** A write-mode projection claims generated addresses and stores them on the Person, under Person locks and in the same transaction as the report and outbox. Repeated projections therefore keep the same address; a rollback keeps neither the assignment nor the outbox. `company_address` has one case-normalized primary key shared by Person and Team owners. Person creation, profile changes, generated assignments and team creation/edit claim the new address before changing the owner row and release the old claim afterward, in the same transaction. Person claims and releases use an owner-scoped `Aggregates` handle and the Person token; Team claims use the same unique index. Multiple generated claims are taken in address order after Person locks in id order. The migration backfills both sources and fails on a collision, without selecting a winner. The importer locks and truncates this derived namespace with its owners; it currently imports neither people nor teams.

R2 item 9 supersedes R1 item 8's assumption that Workspace never writes a Person-owned fact.
