# Spec 0024: Move the Effect line from 4.0.6 to 4.1.0

**Status:** frozen when its PR opens; later changes are dated entries under [Revisions](#revisions) · **Source:** the operator's request of 2026-10-29, [Effect 4.1 release notes](https://effect.website/blog/releases/effect/41) and the installed `effect@4.1.0` sources (`packages/domain/node_modules/effect/src`) · **Branch:** `chore/effect-4.1`, from main `1104c30`.

## Journey

Nothing a user sees moves. A developer runs `bun install`, `bun run ready` and `bun run e2e` on Effect 4.1.0 and gets what she got on 4.0.6, except that `bun run check:cms` and `alchemy.run.ts` are blocked by Alchemy (below). A reviewer reads one change that moves every `@effect/*` pin together, replaces the hand-made Web Crypto adapter with `effect/crypto`, and states which of the 4.1 features it did not adopt and why.

## Goal, constraints, values

- **Goal:** `effect` and every `@effect/*` package (`@effect/sql-d1` and `@effect/sql-sqlite-do` through the root `overrides`) at 4.1.0; `@effect/tsgo` at the newest release that works with TypeScript 7.0.2 (0.63.0, was 0.53.1); every break that bites this repository fixed; every 4.1 feature that deletes or simplifies real code adopted, and no other.
- **Constraints:**
  - **Behaviour does not change.** The stored code hashes (`hashCode` is SHA-256 of the token as lowercase hex), the content-addressed file keys (`fileKeyFor` of the SHA-256 bytes) and the code tokens' shape (`c_` plus 256 random bits as base64url) are the same bytes before and after. Tests assert them.
  - **No patch around a peer.** Alchemy 2.0.0-beta.83 (and the newest release, beta.84) imports `effect/Crypto`, which 4.1.0 removed. It is not patched, aliased or shimmed here. The change stays a draft until Alchemy catches up (the PR's `## Blocked on`).
  - **No `tools/quality` module-graph files.** `globImports.ts`, `resolveImports.ts`, `importSpecifiers.ts`, `globWalk.ts` and the module-graph tests are PR #56's; `packages/db/src/live.ts` and the transaction-proof tests are PR #51's. None is edited.
  - Clean cutover: `webCrypto.ts` keeps its name and its one export, `webCryptoLayer`, and no `Crypto.Crypto` remains anywhere.
- **Values:** the repository's own policy (every Effect plugin rule is an `error`, a suppression is a registered exception) stays; a decision the repository cannot make from its own policy is recorded here and in the PR, not taken silently.

## Open decision (operator-owned): `effecttsgo/prefer-effect-string`

`@effect/tsgo` 0.63.0's `effectNative` preset marks `prefer-effect-string` a `warn` ("with semantic caveats"; the schema default is `off`), and this repository promotes every preset rule to `error`. It fires on 413 native string calls (`slice` 65, `includes` 62, `startsWith` 56, `split` 42, `replace` 30, `replaceAll` 28, `trim` 26, `toLowerCase` 21, `repeat` 20, `endsWith` 16, `indexOf` 13, `matchAll` 9, `padStart` 7, `toUpperCase` 6, and 10 more). Effect's `String` functions are data-last only (`Str.startsWith("x")(s)`), and `indexOf`, `lastIndexOf`, `match`, `search` and `codePointAt` return an `Option` and `split` a `NonEmptyArray`, so about 60 sites change type and need a decision each. The rule has no autofix. The upgrade is not the place to rewrite the repository's string handling, so `tools/quality/diagnosticRules.ts` lists `preferEffectString` in `declined` (one visible switch with this reason), the editor and the lint set it to `off`, and `diagnosticCoverage.test.ts` pins that. Reversing it is deleting that one entry and doing the conversion.
