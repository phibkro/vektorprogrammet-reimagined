# Spec 0006b: races avoided by construction

Status: frozen 2026-10-27. Operator decision: "try avoiding races by construction". Stacked on PR #12 (`chore/effect-4.0.6-drizzle-rc5`).

## Problem

Spec 0006 R6 fixed a deadlock by hand: `MembershipRepository.insert` and `setEnd` now lock the person's row before writing, so two overlapping writes of one person queue instead of deadlocking (SQLSTATE 40P01, about 0.6% of contended rounds). Two facts keep that fix fragile:

1. **The lock is a convention.** Nothing stops the next write to a person's rows (accounts and codes in spec 0007, consents in 0007b, placements in 0011, claims in 0012) from skipping it, and a single-attempt test does not notice.
2. **State transitions are hand-written.** Each repository writes its own `UPDATE … WHERE state = from`. A new repository method can update the state column without that condition and lose an update silently.

## Race classes and the construct that removes each

| Race | Construct (this spec) | Already in place |
| --- | --- | --- |
| Two writes that must not coexist (overlap, duplicate) | — | constraints (unique, check, exclusion) |
| Deadlock between constrained writes on one aggregate | **aggregate lock token** (1) | hand-placed row lock in two methods |
| Deadlock between two aggregates locked in different orders (merge, cross-department change) | **ordered multi-lock** (2) | — |
| Decision on a fact read outside the lock (check-then-act) | **decisions read through the token** (3) | — |
| Lost update on a state machine | **machine-applied transitions** (4) | conditional updates, by hand |
| Side effect done twice, or done without the commit | — | outbox after commit, unique claims |

## Contract

1. **Aggregate lock token.** An aggregate root is declared in `packages/db` with the tables it owns (`Person` owns `membership`, `admin_grant`, and from spec 0007 `account`, `code`; later specs add their tables to the declaration). `Aggregate.lock(Person, id)` requires `InTransaction`, runs `SELECT … FOR NO KEY UPDATE` on the root row, and returns `Locked<Person>` for that id. Every write (insert, update, delete) to an owned table takes a `Locked<Root>` for the row's owner; a write without it does not type-check. The token cannot be constructed outside `Aggregate.lock` (an unexported brand) and does not outlive the transaction that made it.
2. **Ordered multi-lock.** `Aggregate.lockAll(Person, ids)` locks several roots of one type in ascending id order in one statement order; a command that needs two aggregates (`mergePersons`, a cross-department `change`) uses it. Locking two different root types follows one declared global order (the declaration lists roots in order). A second `lock` call for a root already held in the same transaction returns the held token.
3. **Decisions read through the token.** A read whose result decides a write (current memberships for an overlap check, the last active admin, the account state) is a method that takes `Locked<Root>`, so it runs after the lock and inside the transaction. Reads for display stay unlocked and keep passing the SELECT-only role test.
4. **Machine-applied transitions.** A machine's stored state column is written only by `Machine.apply(machine, transition, locked, row)`, which generates `UPDATE … SET state = to WHERE id = $1 AND state = ANY(from)` and returns `Conflict` on zero rows. Repositories no longer write state columns directly. Calculated states (Membership) have no state column and are unaffected.
5. **Ownership is closed over the schema.** A test lists every table with a foreign key to an aggregate root's table and fails when a table is neither owned by a declared root nor declared `NotOwned(reason)`, so a new table cannot escape the construct. A lint rule (the repository's anti-slop rule set) forbids Drizzle `insert`/`update`/`delete` on an owned table outside the aggregate writer module.
6. **Hyperdrive rules hold:** row locks inside a transaction only; no advisory locks, no session state.

## Falsifiers

1. **Type-level:** a write to `membership` without `Locked<Person>`, a `Locked<Team>` passed where `Locked<Person>` is needed, and a hand-made token all fail to type-check (type tests with `@ts-expect-error`, registered).
2. **Ordering:** 300 rounds of two `lockAll` calls over the same two persons in opposite argument order end with no 40P01; the same with a hand-written opposite-order lock (negative control) deadlocks at least once in the same bound.
3. **Overlap races stay fixed:** spec 0006 R6's 300-round insert/insert and extend/insert tests pass through the construct; removing the lock from `Aggregate.lock` makes them fail.
4. **Lost update:** 300 rounds of two concurrent transitions from the same state on one row: exactly one wins, the other gets `Conflict`; a repository method that writes the state column directly fails lint.
5. **Ownership closure:** adding a table with a foreign key to `person` and no ownership declaration fails the closure test; an owned-table `db.insert` outside the writer module fails lint.
6. **Reads never write:** the display reads still pass the SELECT-only role test; locked decision reads are not in that registry (they run inside commands).
7. `bun run ready` and `bun run e2e` pass. Race tests follow AGENTS.md: many rounds, fresh state, each loser's Cause printed on failure, round count stated.

> R3 corrects three statements above. Contract 1 and falsifier 1: an object literal does not type-check as a token, but a token respelled from a real one with a spread does, and the run-time check refuses it (R3 item 2). Falsifier 3: removing the lock fails the two controls that R3 item 1 names every time, and the 300-round races only now and then.

## Out of scope

Serializable isolation and retry loops (a construct that retries hides contention instead of ordering it); Durable Objects per aggregate (rejected for this system: one Worker, Postgres is the source of truth).

## Revisions

### R1 (2026-10-27): how the contract was built, and what the build changed

The contract stands. These are the places where building it showed a better shape than the text, or a fact that the text did not have.

1. **The token and the lock service are the domain's; the declaration, the lock and the writer are `packages/db`'s.** Contract 1 puts `Aggregate.lock` in `packages/db`. A repository interface that takes a token, and a handler that locks, are domain code, and the domain imports nothing from `packages/db`. So `Locked<Root>`, `AggregateRoots` (the roots in their lock order) and the service `AggregateLocks` (`lock`, `lockAll`) are in `packages/domain/src/shared/aggregate.ts`, next to `InTransaction`; only `packages/db` makes a token (`aggregate/locks.ts`, one `Function.cast`, EX-0023). The ownership declaration (`aggregate/ownership.ts`, plain data), its typed handles (`Person.owned.membership`), the lock implementation and the writer `Aggregates` are in `packages/db/src/aggregate/`.
2. **Names.** `Aggregate.lock(Person, id)` is `AggregateLocks.lock("Person", id)` and `Aggregate.lockAll` is `AggregateLocks.lockAll`. `Machine.apply(machine, transition, locked, row)` is `Aggregates.apply(transition, locked, row)`: the generated statement needs the table, which is `packages/db`'s, while the machine's declaration stays in the domain. `AccountRepository.transition` is its one caller. The brand is an unexported `unique symbol`, so an object literal does not type-check as a token (falsifier 1, `aggregate.types.test.ts`).
3. **A token is checked when it is used, not only when it is typed.** `transactional` opens a scope for each transaction level (a nested one is a savepoint) and records the locks that level takes. Every use of a token (`select`, `insert`, `update`, `remove`, `apply`, `findLocked`) asks the running transaction's scope, so a token that was made by hand, that is of another root, that was taken in a transaction that has ended, or that was taken in a savepoint that was rolled back dies as `LockNotHeld`. A failed savepoint drops its locks from the scope, as PostgreSQL releases them with the rollback; a successful one hands them to its parent. A token names a row and not a transaction, so while the running transaction holds a row's lock, an older token of that row reads like a new one. `aggregates.postgres.test.ts` pins each case, and also that PostgreSQL itself held or released the lock.
4. **The order is a defect, not a convention.** Roots are ordered by `AggregateRoots`, and the rows of one root by ascending id. A lock that would come before a lock the transaction already holds is a `LockOrderViolation` defect, found by the first run that reaches it and not by a race. A command therefore locks everything it needs in one `lockAll` before its first decision read. `lockAll` is one `SELECT … WHERE id IN (…) ORDER BY id FOR NO KEY UPDATE`, and a repeated `lock` of a held row sends no statement.
5. **A decision about several people locks all of them (superseded by R2 for the administrators: the admin list's lock replaces this protocol).** A fact that spans people (the last active admin, the last valid admin place) is read in three steps: an unlocked read finds the candidates (the holders of a valid place), one `lockAll` locks the candidates and the person the command is about, and the decision read runs through those tokens (`Aggregates.select(locks, …)` returns the rows of the locked owners only). It is safe because any row that could justify a refusal belongs to a locked owner, so nobody else can delete it before this transaction ends; a candidate who lost the place in the meantime can only cause a refusal that a retry resolves. `AccountEndpoints.deactivate` and `AdminGrantRepository.revoke` both use it, and the 300-round tests run two of them at once in both directions (`accounts.postgres.test.ts`, `teams.postgres.test.ts`).
6. **The writer closes more than the types do.** It fills the owner column from the token and adds `owner = token.id` to every `WHERE`, so a write cannot reach another owner's row. The owner column and a machine's state are not values of an update, and since a value that is not a fresh object literal escapes the compiler's excess-property check, an update or an upsert that names either is a `ProtectedColumn` defect at run time. A row is created in a state (`insert` may set it); afterwards only `apply` changes it. Two methods exist because spec 0007 needs them: `insert` takes `onConflict` (`ignore` for `invite`, `replace` for `code.replace`), and `updateRoot` sets columns of the person's own row (`verifyEmail`, `updateProfile`).
7. **Ownership.** `Person` owns `account` (state column `state`), `admin_grant`, `code` and `membership`. `NotOwned` names `auth_user` (Better Auth writes it outside every domain transaction, and a command only enqueues an outbox message) and `ending_soon_digest` (a claim ledger whose only write is `INSERT … ON CONFLICT DO NOTHING` on its own primary key, so a person lock would only queue the digest behind unrelated writes). The closure test (`ownership.test.ts`) also checks that each owner column is a foreign key to the root's table, that the domain's `AggregateRoots` are the declaration's roots in order, and that a `NotOwned` entry has a reason and names a table that refers to a root.
8. **The lint rule** `vektor-anti-slop/no-owned-table-write` reads `ownership.ts` by relative path and flags Drizzle `insert`, `update` and `delete` of an owned table that were imported from the schema module, anywhere but tests, and `update` and `delete` of a root's own table (creating a root takes no token). A `set({ state })` gets its own message. It reads Drizzle calls and not raw SQL text: a hand-written `sql` statement is not inspected.
9. **Spec 0007's writes moved onto the construct.** Account and code writes, the state changes (`invite`, `activate`, `deactivate`, `reactivate` through `Aggregates.apply`), code delivery and the reset request lock first; `deactivate` locks the person and every admin holder in one `lockAll` (R2 replaced that with the admin list's lock, then the person). `accountDelivery` (the separate delivery transaction) locks the person before it replaces the code. Better Auth's hooks and the principal reads stay unlocked display or request-time reads.
10. **R6's negative control changed meaning.** The test that made the update unconditional used to find an illegal sequence because the conditional update was the only guard. With the lock first, every command decides on a row it holds, so the same replay is legal; the test now asserts that, and it fails when the lock is taken away. The conditional updates stay as the contract of `setEnd` and `remove`.
11. **Facts about the toolchain.** The driver reports SQLSTATE 40P01 as `SqlError/DeadlockError: deadlock detected`, and the printed Cause does not show the code. A hand-written opposite-order lock takes `deadlock_timeout` (1 s) to be detected, so the negative control sets `SET LOCAL deadlock_timeout = '20ms'` in its own transaction (a test-only statement; no production code sets session state). `InTransaction` is declared with the `@effect-leakable-service` tag, because `AggregateLocks.lock`, `lockAll` and `AdminGrantRepository.revoke` now return effects that require it, and the lint configuration defines the tag. `typescript/no-unsafe-type-assertion` stays on, so the three places that state a type the compiler cannot derive (the token, the typed declaration, the rows of a statement on a generic table) are one `Function.cast` each, registered as EX-0023; the type cases are registered as EX-0024.

### R2 (2026-10-27): the admin list is a root, and one rule counts the administrators (issue 17)

R1's decision about the last administrator was wrong in a way that R1's own tests could not see, and the lead's probe found it: two Active administrators A and C, A deactivates C while C revokes A's place. R1 serialised the two commands (both locked the holders of valid places), but its two checks counted differently. `AccountRepository.isLastActiveAdmin` counted the holders of a valid place that have an Active account; `AdminGrantRepository.revoke` counted every valid place. So the revocation that ran after the deactivation still counted the deactivated administrator's place, found that another place was left, and removed A's: no Active administrator held a place any more. The same hole lets a stale principal of a deactivated administrator (its request began while the account was Active, and a principal is not rechecked) revoke the last place that an Active administrator holds. The contract stands; the text changes in these places.

1. **One rule, one read.** A place counts as an administrator's when it ends after the cut-off and an Active account holds it. `repositories/adminPlaces.ts` (`activeAdminPlaces`) is the only read of that set, and both decisions use it: `deactivate` with `now` as the cut-off, `revokeAdmin` with the end of the current semester (each as before). A place of a Deactivated or an Invited account does not count in either decision, so the two cannot disagree about who is left.
2. **A root with no table of its own.** `AdminList` joins `AggregateRoots` in front of `Person` (`["AdminList", "Person"]`). Its one row (`admin_list`, `id = 1` under a `CHECK`, inserted by the migration `admin_list_seeded`; `ADMIN_LIST_ID` names it) holds no data and exists to be locked, so `Ownership` declares it with `owns: {}` and `EntityName` gained `"AdminList"`. `lockAdminList` (domain) is `AggregateLocks.lock("AdminList", ADMIN_LIST_ID)`. The global order is the admin list first, then people in ascending id: a person's lock before the list's is a `LockOrderViolation`, found by the first run that reaches it (`aggregates.postgres.test.ts`). This supersedes R1 item 5: the unlocked read of the candidates and the `lockAll` of the holders are gone, and so is `AccountRepository.adminHolders`, because one lock serialises every decision about the whole list and needs no candidate set. A person who gained a place between R1's unlocked read and its lock was never locked; nobody can now.
3. **Who takes it, and what cannot be done without it.** `deactivate`, `reactivate`, `grantAdmin` and `revokeAdmin` lock the list before any person, and the decisions take its token: `AccountRepository.isLastActiveAdmin(adminList, personId, now)` and `AdminGrantRepository.revoke(adminList, holder, id, validAfter)` check it (`LockNotHeld` when this transaction does not hold it), and `AdminGrantRepository.create(adminList, locked, draft)` takes it as well, so a place cannot be given or taken, and the last administrator cannot be decided on, without the lock: a person's token in its place does not type-check (`aggregate.types.test.ts`). `revoke` finds the place before it locks its holder, which is safe because every change of a place holds the list. R1 item 9's `deactivate` that locked the person and every admin holder is now the list, then the person.
4. **What the lock does not cover.** Writes that can only add an Active administrator (`activate`, which is the code flow of spec 0007) do not take the list: they cannot turn "another one is left" into "none is", and an `activate` that lands between a decision and its commit can only make a refusal that a retry resolves. `reactivate` and `grantAdmin` also only add an administrator and take the list anyway, so that every write of a place and every change of an account's state that a decision could be waiting for queues behind the decisions, and so that the rule to state and to review is one sentence ("a command that changes a place or deactivates or reactivates an account locks the list first") instead of an argument about which writes are monotone. `AccountRepository.transition` itself does not demand the list's token; that a removal holds the list rests on `deactivate` and `revokeAdmin` and on the test that shows each of the four commands waiting for the list's row lock. A new command that removes an administrator must lock the list first, and the type of `isLastActiveAdmin` is what makes forgetting it cost a compile error, not a race.
5. **Falsifiers, and what removing each guard does.** `adminList.postgres.test.ts` (round counts stated, each loser's Cause printed on failure, fresh state in every round): 300 rounds of A deactivating C while C revokes A's place, through `AccountEndpoints.deactivate` and `TeamsEndpoints.revokeAdmin` as two admin principals: exactly one command wins, the loser is `Conflict` (the deactivation) or `ValidationFailed` on `id` (the revocation), and one place held by an Active account is left; the same 300 rounds with every deactivation's write held back 15 ms, so that the other command always decides in between; the control, the same two decisions written by hand under each person's own lock only (R1's protocol with R2's counting rule) with the interleaving forced by a barrier, which leaves no Active administrator with a place in all 30 rounds; the stale principal of a deactivated administrator, which is refused (`ValidationFailed` for the revocation, `Conflict` for the deactivation) while counting every valid place, the old rule, finds another place left in both; and each of the four commands, run while another transaction holds the list's row lock, waits on it and finishes after the release (a person's lock alone, the control of that test, does not wait). Weakening only the list's lock to `FOR KEY SHARE` (which two transactions can hold together) fails the 300-round race in all 300 rounds, with and without the delay ("2 commands succeeded, not one; 0 places held by an Active account are left"), the lock-wait test, the 300-round race of two revocations of two different people (`teams.postgres.test.ts`) and spec 0007's 300 rounds of racing deactivations. Counting every valid place again fails the 300-round race in both variants, the stale principal test, the PGlite test that a deactivated account's place does not count, and spec 0007's racing deactivations. The domain's in-memory fakes log each lock, and `commands.test.ts` asserts `AdminList:1` before `Person:n` for a grant and a revocation.
6. **Facts.** `grantAdmin` and `revokeAdmin` take their instant and id as the text and numbers that a request carries (`until` is an ISO string at the endpoint; a `DateTime` there is a `ValidationFailed`), and a test that shares one database must clear the places and accounts that an earlier test left (`noAdmins`), because the rule reads every administrator in the database. The new test file declares itself a node composition root in `vite.config.ts`, like `accounts.postgres.test.ts`, because the account commands need `Crypto` and the test takes it from `NodeServices` (EX-0006). No new exception is registered.

### R3 (2026-10-27): review round 1 of the pull request: what falsifier 3's control is, what a token's type gives, and whom an upsert may write

Two reviewers ran PR 22 at `715a418` and mutated the construct. The contract stands. These are the places where the text claimed more than the code and its tests gave.

1. **Falsifier 3's controls are two tests that fail every time; the 300-round races are a guard.** Falsifier 3, spec 0006 R8 item 2 and the pull request said that removing the lock from `Aggregate.lock` makes the 300-round insert/insert and extend/insert races of spec 0006 R6 fail. They mostly stay green. Mutation M1 deletes `.for("no key update")` from `aggregate/locks.ts` and runs `teams.postgres.test.ts` five times: insert/insert failed in 2 runs (SQLSTATE 40P01) and extend/insert in none; the review's twelve runs saw 4 and 1. That is R6's own figure (about 6 contended rounds in 1,000 deadlock), and it means that a green run of those races, with the lock or without it, shows little about the lock. A control that passes when it should fail is not a control (AGENTS.md). The controls of falsifier 3 are the two tests of `teams.postgres.test.ts` that failed in all five M1 runs, and whose titles now say so:
   - "falsifier 3, lock-removal control (spec 0006b R3): an insert waits for the person's row lock before it writes anything". Another transaction holds the row lock, and the test reads `pg_stat_activity` for the insert waiting on it. Without the lock the insert does not wait (`expected +0 to equal 1`).
   - "falsifier 3, lock-removal control (spec 0006b R3): the person's lock alone keeps the successes legal, even when the update is unconditional". It is R6's replay with an unconditional `UPDATE`. With the lock every command decides on a row it holds, so the replay is legal. Without it all six attempts of each of the five runs found illegal sequences (1 to 10 each, such as "endEarly from Vår 2027 after the end was HOST 2026").

   The two 300-round races stay as the guard of R6's contract with the lock in place (every loser is `AlreadyExists`, never a deadlock), and are no longer said to fail without it. Under M1 the two 300-round revocation tests of R2 also failed, in round 1 of all five runs (both revocations succeed), because the admin list's row lock is what queues them. AGENTS.md states the rule: a control fails every time, and a race that fails without the lock only sometimes is a guard.

2. **What a token's type gives.** Contract 1 and R1 item 2 said that a hand-made token does not type-check. That holds for an object literal. A token of one row can be respelled as a token of another row of the same root, with no cast and no directive: `const ofSeven: Locked<"Person"> = { ...ofFive, id: 7 }` compiles, because the spread copies the brand and `id` is an ordinary property. So the types promise three things: a write needs a token, a token of one root is not a token of another, and an object literal is not a token. They do not tie a token to its row. The run-time check does (R1 item 3): every use asks the running transaction's lock registry, so a token respelled for a row that this transaction does not hold dies as `LockNotHeld`, and no read or write reaches the row. While the transaction does hold the row, a respelled token reads like the one that `lock` returned, as R1 item 3 says of an older token. `aggregates.postgres.test.ts` adds the respelling to its run-time cases, and `aggregate.types.test.ts` pins the type fact with a case that compiles under no directive (if a stricter type ever refuses it, that file stops type-checking and this item is out of date). The doc comment of `Locked`, `packages/db/README.md` and the pull request say this and no more; they no longer say "unforgeable".
3. **An upsert writes only the owner's row.** R1 item 6 said that the writer adds `owner = token.id` to every `WHERE`. That held for `update` and `remove`, not for `insert(…, { action: "replace" })`, whose `ON CONFLICT (target) DO UPDATE` had no owner condition: a target that leaves the owner column out (`code` has `code_hash_unique`, a unique index on the hash alone) would rewrite another owner's row without that owner's lock. No live path did: `CodeRepository.replace` targets `(purpose, subject)`. `Aggregates.insert` now sets `setWhere: owner = token.id`, so a colliding row of another owner stays as it is and the statement returns no row. `aggregates.postgres.test.ts` upserts on `code_hash_unique` as a second person (the first person's row is unchanged and nothing is returned) and as the first (the row is replaced); without `setWhere` the first half fails.
4. **The lint rule's tests are a gate.** The `RuleTester` cases of `no-owned-table-write` are the executable evidence for the lint halves of falsifiers 4 and 5, and no gate ran them: `tools/oxlint` was not a workspace package, `vp run -r test` skipped it, and neither `bun run ready` nor CI called `node --test` (CI run 40460283172 ran 532 workspace tests and none of the 110 rule cases, those of the five older rules included). `tools/oxlint/package.json` now has the `test` script `devenv shell -- node --test "anti-slop/rules/*.test.ts"` (through devenv like every other package's script, which pins Node 24), so `vp run -r test`, the pre-push hook and CI run all six rule tests. A rule that stops reporting fails them: with the one-line mutation that drops `insert` from the rule's table of writes, 4 of the 110 cases fail, `vp run -r test` exits 1 within a second, and `vp run` stops the tasks of the other packages.
5. **Facts the review corrected.** `packages/db/README.md` said that the one `SET LOCAL` is in a test. There are two, both in tests and each ending with its own transaction: `aggregates.postgres.test.ts` shortens `deadlock_timeout` in R1 item 11's control, and `codecs.postgres.test.ts` sets a time zone. No product code sets session state. The pull request has two migrations, not one: `admin_list` creates the table and rewrites the `audit_log_entity` check so that it allows `AdminList`, and `admin_list_seeded` inserts the row. No exception is registered or changed.
6. **The TLA+ model of membership writes describes the construct.** The model of PR 18 (`.agents/skills/verify-membership-writes`) described the code before this spec and its digest check reported drift. It now translates the code statement by statement (`Shapes.tla`): a command is find, lock, read and write (`beginTransition`, `addMember`); the lock is one `SELECT … ORDER BY id FOR NO KEY UPDATE` through `AggregateLocks`, and the writes take its token; the admin list is a lock key before every person, which `grantAdmin` and `revokeAdmin` take first; the registry's refusal of a lock out of order is a step that sends no statement; `lockAll` over two persons is one ordered statement, so two acquisitions, lowest first. The property `NoWaitInCheck` is new (with every write under the person's lock, none waits inside the exclusion check, which is contract 1 as a property), and `run.sh` lists 27 runs that are all as expected: `current-code`, 10 reach goals, 9 variants that must fail and 7 runs that must pass (the fixed story, the variants that the code survives, a command through the construct and `lockAll`). What the model adds to item 1: TLC finds the deadlock of mutation M1 (`lock-takes-no-row-lock`) in its first interleavings, where the 300-round race found it in 2 of 5 runs; and it shows that the conditional UPDATE and the lock each keep every commit legal alone (`decide-before-lock` and `setend-unconditional` pass) and break it only together (`decide-before-lock-unconditional`), which is R1 item 10 as a verdict of the model. The PostgreSQL facts that it takes are pinned in `membershipWriteModel.postgres.test.ts`, which R3 brought to the token API (nine of its tests died as `LockNotHeld`): a probe that `lockAll`'s statement takes its rows lowest first, one at a time (the mutations that drop its `ORDER BY`, flip it to descending and drop the row lock each fail it), and one test per membership command that it waits for a person's lock that another session holds before it writes. `run.sh --code` runs that file with the aggregate and admin list tests. The model does not check what the admin list's lock protects (whether an Active administrator is left): R2 item 5 races that with controls. The writer scan of `run.sh` listed no writer of `membership` at all, because the writes go through `aggregates.insert(…, owned.membership, …)`, and it listed a RuleTester fixture string as one; it now anchors on the handle `owned.membership`, ignores `*.test.ts` and accepts a directory in the coverage block (`packages/db/src/aggregate`).
