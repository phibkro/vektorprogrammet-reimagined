# Alchemy Domain beta.84 PostgreSQL spike

**Status: spike complete; verdict: partly, do not adopt as the production runtime.** The PostgreSQL platform and model falsifiers, documentation checks, and same-machine latency comparison ran. Profile-field erasure is now implemented and tested with an explicit pseudonymous-history residual; it is not a claim of GDPR-complete erasure. Adoption remains blocked by residual re-identification risk and missing legacy-row bootstrap.

## Platform implementation and contract boundary

`spikes/alchemy-domain/src/postgresPlatform.ts` is 930 lines. Supporting platform schema/code: `ddl.ts` 105 lines, `rows.ts` 109, `errors.ts` 11; **930 platform implementation lines (1,155 including those three support files)**. These counts are `wc -l`, not a complexity measure. `ddl.ts` creates spike-only tables, including AdminList read models, not repository migrations.

The aggregate send path locks the aggregate instance row `FOR NO KEY UPDATE`, checks the `(aggregate,id,command_id)` receipt, calls `kit.handle`, conditionally updates version/state, appends events, stores the receipt and non-projection deliveries, and applies projections before the transaction commits (`postgresPlatform.ts:123-235,575-704`). The platform contract directly requires single-writer-per-id, commandId deduplication, atomic events/state/receipt/deliveries and ordered at-least-once delivery (`node_modules/@alchemy.run/domain/src/Platform.ts`, `AggregateStore`).

The projections use a **custom synchronous SQL hook**, not beta.84's ordinary asynchronous projection delivery: `persist` filters projection-target deliveries and calls `projections.apply` inside the `send` transaction; it separately registers the remaining delivery outbox drain with `SqlClient.afterCommit` (`postgresPlatform.ts:575-615). Membership projection writes the repository table; AdminList writes spike-owned `alchemy_admin_account`and`alchemy_admin_place`read models rather than the production`account`and`admin_grant`tables. Consequently a projection handler that throws aborts the aggregate transaction; the receipt only becomes visible after projection work and transaction commit. All handlers run through the transaction-bound`SqlClient` captured by the model layer. Contract tests exercise rollback of an outer transaction, a projection failure rollback, receipt dedupe and after-commit consumer delivery (`test/platform.contract.test.ts:395-488,687-743`).

Upstream `ProjectionKit.run` is specified to return only after writes succeed and the platform records progress only then. Its regular `ProjectionStore.receive` accepts/dedupes input and processes per key in order (`node_modules/@alchemy.run/domain/src/Platform.ts`, `Projection.ts`). The in-memory implementation forks projection work after the command; the beta.84 Cloudflare Durable Object implementation is the only upstream production platform (`@alchemy.run/cloudflare` beta.84 source, Apache-2.0; source pin and detailed review recorded by the read-only provenance investigation). Neither upstream implementation makes arbitrary SQL projection writes atomic with the originating aggregate write. The spike's guarantee is conditional: projection handler statements must use the exact same transaction-bound `SqlClient` as the platform. A second pool/client or non-SQL external write would break that guarantee. Hyperdrive/Workers, crash/restart, lease expiry, cross-process delivery, and an actual deployed adapter were not exercised.

Important differences/risks from beta.84's ordinary delivery semantics: the spike intentionally returns a stronger read-your-write result by waiting for synchronous projections, but a projection defect blocks the command rather than leaving the event committed for projection retry. It does not retain accepted projection input rows, so rebuild requires replaying event history. It stores rejected command receipts, unlike both the upstream in-memory and Cloudflare stores, which return on rejection before storing a receipt. Policies and views are delegated to the in-memory platform and are not durable across process restart; a successful policy `deliver` enqueue is not equivalent to its side effect succeeding durably. Stream factories now fail explicitly rather than silently falling back to an in-memory stream. The platform does not provide a durable WorkflowEngine; models with sagas are unsupported and fail at model construction. Scheduled commands require an external caller to invoke `PostgresPlatformControl.fireDue`; no scheduler was running here.

## Model port, authorization and privacy

The spike defines Person membership events/state/commands in `src/model/person.ts`, AdminList events/state/commands in `src/model/adminList.ts`, membership projection writes to the repository table, and admin-account/place read models under the spike's `alchemy_admin_*` tables (`src/model/projections.ts`, `ddl.ts`). Membership interval overlap and transition decisions were source-compared against `packages/domain/src/teams/commands.ts`, `Teams.MembershipMachine`, and PostgreSQL's `membership_no_overlap` exclusion constraint. The last-admin count uses one aggregate state containing both account activity and admin places, matching spec 0006b R2's invariant ownership rather than splitting decisions across roots.

The guard calls the existing authorize over packages/domain/src/declarations.ts GrantTable, not a copied role table. Its principal comes from CurrentPrincipal rather than caller-controlled input. Fact resolution uses SELECT queries, but the model was not run through a real Api request, so declaration parity and unauthorized-before-decide are not behaviorally proven. The check:docs run passed and generated teams, accounts and commands blocks matched (falsifier ledger).

**Erasure is met for the spike profile store, with a pseudonymous residual.** Person aggregate state and events do not store name, email or phone. The internal-only erasePerson maintenance command emits PersonErased containing only personId; it is not registered in a public RPC or user grant declaration. The in-transaction PersonProfileRows projection deletes the corresponding spike-owned alchemy_person_profile row. The PostgreSQL test seeds synthetic name/email/phone markers, confirms the pre-erasure scan finds each marker only in alchemy_person_profile, then scans every public base table after the command and finds zero matches. It also creates a MembershipAdded event before erasure, asserts that PersonErased carries the target id, and confirms both events and the one-membership aggregate state remain. AdminList account/grant history is outside this Person-only erasure operation and remains. The test covers this spike profile store, not the repository-owned person row, external identity records, backups or logs. The shared IDs and relationship/activity histories are pseudonymous personal data and may be reidentified through those systems or backup copies. Retention still needs cross-system deletion propagation, legal-hold rules, and expiry or key-shredding of backups and logs. No GDPR-complete claim is made.

Crypto-shredding was not prototyped: a per-person envelope key could encrypt the profile fields and make retained backup copies unreadable after key deletion, but would require encryption before writes and key-retention/rotation operations. It would not remove the ID-linked membership/admin history.

A further adoption risk identified by source audit: event-sourced aggregates start empty, while imported or already-written relational rows may exist without corresponding aggregate events. On those rows, a last-admin or no-overlap decision can use incomplete state; projection upserts can also overwrite existing account status. `AggregateStore.seed` exists but the model does not bootstrap aggregate history from repository data. This gap needs a defined migration/bootstrap before production use.

## Friction, provenance and reusable patterns

Installed versions: Effect 4.0.6; `@alchemy.run/domain` and `alchemy` 2.0.0-beta.84. `@alchemy.run/domain` declares peer `effect:^4.0.5` and exact peer `alchemy:2.0.0-beta.84` (`node_modules/@alchemy.run/domain/package.json`). The repo pins the Alchemy packages at beta.84 while its Effect catalog is 4.0.6. No OAuth credential was needed to inspect the installed npm package or run its local PostgreSQL contract tests; the predecessor's provider OAuth 403 was not retried. This run did not measure package-install/build friction or validate another Effect patch release.

Package provenance: npm package metadata says author Sam Goodwin, repository `https://github.com/alchemy-run/alchemy`, package directory `packages/domain`, `Apache-2.0`. The read-only source audit matched the installed `Platform.ts`, `Projection.ts`, `InMemory.ts`, `Model.ts`, and Cloudflare `Domain/index.ts` against upstream tag `v2.0.0-beta.84`, commit `c78e72bc1c172ede20747ac0b8a2175ef1de31a1`. Permalink: `https://github.com/alchemy-run/alchemy/tree/c78e72bc1c172ede20747ac0b8a2175ef1de31a1/packages/domain`. Copying upstream code requires preserving Apache-2.0 notices and marking modifications. This spike's PostgreSQL implementation was authored from the published platform interface, not copied from the Cloudflare implementation. The shipped domain package itself has no NOTICE file; consult the upstream repo root license/notice when reusing code.

Ranked patterns worth reusing regardless of runtime adoption:

1. **Given/when/then Story** — `@alchemy.run/domain/src/Story.ts` plus `skills/alchemy-domain/references/testing.md`; Apache-2.0, above upstream commit. It makes a useful pure decision/evolution specification. Land tests in `packages/domain/test/` beside team/account command rule tests; do not move infrastructure or API behavior into Stories.
2. **CommandId receipts** — `Aggregate.ts`'s send contract and `Platform.ts` `AggregateStore`; same provenance/license. The existing repo already has database idempotency/outbox patterns in `packages/db/src/aggregate/` and command handlers; compare semantics before adopting a second receipt table. In particular, decide explicitly whether rejected answers are cached—the spike diverges from upstream.
3. **Typed read-your-write checkpoints** — `Projection.caughtUp`, `View` atLeast options and per-source checkpoints in `Model.ts`/`Platform.ts`. Keep any adaptation alongside the existing aggregate/read-model boundary in `packages/db`; do not imply the synchronous spike hook has the same semantics as an asynchronous production platform.
4. **Per-key ordered delivery log and lease** — upstream Cloudflare projection queue (`packages/cloudflare/src/Domain/index.ts`) is Apache-2.0, but is platform-specific. Reuse the repository's richer `packages/db/src/repositories/outbox.ts` / `OutboxDelivery` rather than transplanting a second generic queue. If needed, add explicit per-key ordering there, with its tests.
5. **Policy/saga separation** — upstream `Policy.ts`, `Saga.ts`, `Model.ts` are Apache-2.0. Policies map to existing after-commit outbox handlers; a saga needs a real durable workflow engine and compensation policy, neither provided by this PostgreSQL spike. Do not claim saga support by composing in-memory workflows.

## Latency and final disposition

**Measured on 2026-10-27:** 100 timed createMembership commands per path after 20 warmups, interleaved repository-first/Alchemy-first over the same disposable PostgreSQL database and 30-connection pool. Fixture construction was outside the timer; monotonic Clock nanoseconds enclosed each complete command. Repository TeamsEndpoints.createMembership + transactional path: p50 3.319 ms, p95 3.941 ms, max 6.338 ms. Alchemy Person command (SELECT facts + transaction with synchronous SQL projection): p50 4.253 ms, p95 5.001 ms, max 6.287 ms; p50 was 28.1% slower. Evidence: /tmp/alchemy-latency-postgres.log. This is a local command sample, not Hyperdrive/Worker/Neon production latency.

**Verdict: partly; do not adopt as the production runtime yet.** The corrected #17 positive test asserts all 300 row-lock races and passes. The forced no-lock/no-version-guard control, repeated five times, shows why the row lock is still needed for a typed serialized outcome: the event sequence primary key preserves activePlaces=1 by rejecting one command with a PostgreSQL UniqueViolation. That DB guard, not the platform row lock, preserves final-state cardinality while exposing an infrastructure failure instead of a typed rejection; projection-key upsert is not the cause. The 300-round membership stress is protected by the repository membership_no_overlap exclusion constraint, not shown to depend on the platform lock. Profile erasure is met only for the spike profile; IDs and membership/admin history remain pseudonymous and reidentifiable through other systems and backups. Missing legacy-row bootstrap, the narrow 28.1% p50 latency increase, and untested Hyperdrive/Worker/crash-restart behavior still block production adoption.
