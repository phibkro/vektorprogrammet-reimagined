# Prototype infrastructure

This root uses the official Supabase and Cloudflare providers. Terraform owns the selected existing project's Auth and Data API settings, and one Cloudflare Worker script, its asset upload, bindings and cron triggers. It does **not** create, delete or own the Supabase project, its database schema, users, Storage buckets, or Cloudflare DNS. The application migration/setup commands own schema, synthetic users and buckets. Do not also deploy this Worker with Alchemy, Wrangler, `cf`, or another Terraform state: every deploy replaces Worker version settings and bindings. The old Neon/EmDash preview deployment and teardown workflow is removed; no automatic preview deployment replaces it.

Terraform requires `capture_smtp` with host, port, user, password and sender_email and configures Auth to use it. The operator must establish independently that it is an actual non-delivering capture sink reachable by hosted Supabase; Terraform cannot prove that property. Until that evidence exists, no apply or hosted Auth email flow is safe. Local Supabase CLI uses its own captured SMTP. Production SMTP requires separate operator authority and credentials and is outside this root. This configuration is a prototype only, not authority to deploy. No apply, import, project creation, remote changes or real messages are authorized by its presence. It requires an existing, **dedicated synthetic-data** Supabase project; never point it at production. `DEPLOYMENT` is fixed to `preview`, and no live mail, Slack or Workspace bindings are supplied to the application. Supabase Auth can send mail independently of these Worker bindings: use only synthetic/test addresses and an independently verified non-delivering SMTP/test sink. Disabling signup does not disable invitation or recovery email. Do not test those flows against real recipients. Supabase's hosted default SMTP is not a capture sink.

## Local state and credentials

Install Terraform and initialize from this directory with `terraform init -backend=false`. The committed provider lock pins the provider releases. State is local and ignored, but **is not encrypted**: provider state and saved plans can contain database credentials, Supabase secret keys, and Auth configuration even when Terraform marks inputs sensitive. Restrict filesystem access; never commit, upload or log state, plans, tfvars, provider debug output or credentials. Arrange an encrypted, access-controlled state backend and locking before any shared use; this root deliberately configures no remote backend. The providers authenticate through `SUPABASE_ACCESS_TOKEN` and `CLOUDFLARE_API_TOKEN`; use scoped operator-provided tokens. Provide inputs via protected environment variables `TF_VAR_*` or an ignored protected tfvars file. Secret inputs are `database_url`, `supabase_secret_key`, and `turnstile_secret_key`; no secrets are outputs.

`supabase_project_ref` identifies the project; `supabase_url`, publishable and secret keys and `database_url` must all come from that **same** project. Supply `site_url`, the actual HTTPS origin; this also sets the Auth site URL and redirect allow-list. The API schema setting excludes `public` so application domain tables are not exposed through PostgREST; verify RLS and grants independently, including for any other exposed schemas. Settings not named here remain the provider/API's responsibility: inspect the imported configuration and plan before approval. The Supabase provider's settings resource supports partial updates; imports can bring other settings, possibly secrets, into local state. Review changes before applying. Auth `disable_signup` blocks self-service signup, not administrator creation/invitation.

For an existing project, import only its settings (not the project), after initializing and setting all required variables:

```sh
terraform import supabase_settings.prototype "$SUPABASE_PROJECT_REF"
terraform plan
```

Import contacts the provider and writes local state. It needs separate operator authority; neither command was run here. There is no implicit `supabase_project` resource to create or destroy an existing project. Do not apply a plan that replaces, clears or unexpectedly changes existing settings.

## Worker artifact contract

Build the Start app using its Cloudflare Vite plugin before planning. Terraform reads `apps/web/dist/server/wrangler.json`: entry, client asset directory, compatibility settings, cron triggers and rate limits come from the generated configuration. It uploads the emitted `.js` and `.mjs` server modules by their relative names, excluding the entry and source maps. The observed build contains `index.js`, 104 additional modules, two crons and one rate limiter. Auth invite and recovery templates come from `supabase/templates/`.

The provider supports native [asset directory uploads](https://developers.cloudflare.com/changelog/post/2025-10-09-assets-terraform/) since 5.11; this root pins 5.28.1. The local artifact mapping was evaluated, not deployed. `terraform validate` does not prove the upload or runtime behavior. If the build introduces additional module types or bindings, this mapping must be updated before release. This root owns the Worker version and assets; do not upload them with another tool. Supply the account ID, a unique Worker name and test Turnstile keys.
